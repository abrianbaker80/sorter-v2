# P2C6P-A r1 — convergence and performance preservation

## Decision

Converge ordinary sorting to the golden implementation in small, tested slices. Preserve the physical C4 and accepted Smart Bin contracts behind explicit mode/adapter selection. **P2C6B remains blocked.** The present candidate is not yet qualified as a performance-equivalent replacement for golden live: the same TwoPiece configuration selects a different controller, several upstream continuous-operation fixes are missing, and ordinary routing still consults pre-existing Harvest storage.

This is source analysis, not a benchmark or current hardware inspection. The user's continuously observed roughly 7–9 PPM is a reference, not an exact laboratory threshold. Firmware v0.8.1 / `8d560d26` / distribution-v1-2 and existing live tuning remain protected. No change to either is proposed.

All abbreviated source paths below are relative to `software/sorter/backend/`. `comparison.json` contains exact A/B/C blob IDs, SHA-256 hashes, slice attribution, and a decision/reason for every changed production/configuration path in scope. A missing blob is represented by null, not by an empty-file hash.

## 3. Physical C4 architecture: preserve contracts, select them explicitly

### Golden path versus candidate path

Golden's TwoPiece controller tracks visual pieces, submits asynchronous classification, keeps one positioned head, advances a real drop slot, and uses the distribution state machine with loose-clump protection. Candidate `state_machine.py` lines 109–114 constructs `PhysicalC4Controller` for **both** TwoPiece and indexed mode values. Its startup needs marker source/reference/mapping, establishes a ten-position FIFO, and runs reject recovery for unknown custody. This semantic redirection is present with Smart Bins disabled.

The user supplied board/firmware and observed performance, but not the current camera topology, active mode, pocket geometry or marker mapping. No machine configuration or hardware was inspected here. Consequently “the actual machine requires ten-pocket marker control” is **unproven**. Golden operation demonstrates that its ordinary path works on the reported machine; it does not prove physical FIFO contracts are unnecessary for future native releases.

Minimum physical architecture is one controller/owner, one FIFO and generation map, one tracked marker positioner, one C3 transfer episode/recovery owner, one deterministic index planner and one distribution handoff. Add the durable bridge/completion adapter only for native Smart Bins. Recognition needs a bounded asynchronous result contract; all optional rolling/freefall/history views and speculative scheduling are not prerequisites for custody safety.

This is a product mode boundary, not a workaround or a request to remove safety checks. An occupied machine cannot change owners in place. Mode changes need explicit configuration/migration design, empty or reconciled custody and later separately authorized qualification. No removal, mode switch or machine edit happened here.

### Other performance-sensitive candidate behavior

- `PhysicalDistribution.observe()` exposes one current positioned slot and can wait behind a pending recognition result. `physical_runtime.tick()` observes twice per planning tick; DB guards in `clear()` can therefore repeat. Measure queue/head blocking and overlap, not only motor speed.
- `marker_source.sample()` fetches `/snapshot.jpg` and health with a 0.75-second per-request timeout, then decodes/fits. These are potential lock-held stalls, not measured durations. Candidate per-stage marker deadlines may legitimately extend the total episode beyond one stage budget; measure total and each stage.
- C3 release waits for stopped plus exact target, and holds unsafe C3 motion against C4 indexing. Preserve safety, measure lost overlap and commanded-versus-observed movement separately.
- `crop_quality.py` retains more geometrically valid views than golden's relative sharpness cutoff; recognition journeys copy full scenes/history and run one provider request per UUID. This can change memory, payload and latency, even though provider work is asynchronous.
- Candidate globally enables color correction with a C4 role allowlist where A has the master gate off. Preserve the optional calibrated feature, but ordinary golden comparison must not silently alter input pixels.
- Candidate flap code checks all passage flaps and deduplicates accepted pending targets. This is intentional safety behavior with bus/settling cost to measure; removing checks is not an acceptable optimization.

Counts below are source-level call/transaction counts for successful paths, **not milliseconds**. A commit call on an empty transaction is not necessarily a disk flush. FULL on WAL means durability is requested on actual writes; SQLite/OS/storage determine latency. Critical connections use `BEGIN IMMEDIATE`, foreign keys and `synchronous=FULL`; local legacy connections explicitly use NORMAL. Read-only `_readonly()` opens `mode=ro`, sets query_only, starts one snapshot and rolls back on exit.

Successful native release from an **already reserved** piece has seven FULL write commits: intent, exit, retained handoff, delivery, publication attempt, publication success, CLOSE. Including one reservation makes **eight**. Preview/lookup, faults and retries add transactions. There is no honest single total read count: trims, observations, predecessor checks and admission polling vary. The table states each call's multiplier and must be used to instrument the actual total.

### Instrumentation design for a later authorized slice

Instrument `critical_transaction`, `_readonly`, ordinary occupancy reader, native adapter transitions, `Positioning`, `Sending`, and existing coordinator profiler. Use monotonic spans for connection/open, schema checks, BEGIN lock acquisition, statements/rows, commit, readback and total lock-held time. Tag source hash, mode, piece UUID, reservation/attempt, stage and outcome; hash/redact public identifiers as needed. Count calls and actual nonempty commits separately. Record cold first use, warm operation, trim/retry paths and queue depth. Emit bounded asynchronous metrics; no per-frame synchronous logging.

Measure on disposable seeded stores at 0/1k/10k/100k historical completed follow-ups, multiple machines, late holds, duplicate observations and concurrent retention. Record query plans and rows examined. Compare no-adapter ordinary, P1/P2B ordinary eligibility, and explicitly injected native adapter independently. Test lock contention and storage fault handling without motion. Preserve late-hold correctness when designing a bounded outstanding-obligation projection; blindly filtering CLOSED rows loses accepted late-blocker semantics.

Proposed source performance gate: no full-history scan in an ordinary tick; native current-authorization work should depend on outstanding obligations, not all delivered history. On the intended host/storage, warm native DB critical-path p95 should fit within 5% of the same-lot golden median inter-completion interval (about 0.33–0.43 s only as an illustration from 7–9 PPM), with p99 reported and no timeout-driven routine holds. This is a budget to validate, not a measured claim or permission to relax FULL durability. Record actual aggregate cost per piece before setting final thresholds.

## 5. Harvest isolation verdict and four baseline failures

**P2C6A journal isolation passes source inspection; whole-candidate ordinary Harvest independence fails.**

- `PhysicalNativeBridge` and `NativeCompletionAdapter` are injection points; no production constructor call was found. P2C6A integration modules have no production motion/startup construction. The inspection import in `smart_bins_delivery.inspect_recovery` is local and read-only.
- `smart_bins_harvest_integration.inspect_on_connection` returns empty blockers when no local external Harvest records and no journal version exist. Missing schema alongside records is surfaced, not initialized. Known operations return project scope; missing operation identity/schema yields machine scope. No physical recovery authority is returned.
- `project_harvest_projects.py` uses the extension only for supplied integration requests; ordinary untagged retirement/undo tolerates its absence via `is_integrated`. No extension initialization occurs on import.
- However, B/C `Positioning._reserveHarvestRoute` calls `project_harvest_runtime.reserve_piece`. GlobalConfig always supplies a Harvest root. `_store_for_root` constructs `HarvestProjectStore` once (which initializes the legacy Harvest store); every `reserve_piece` calls `has_active_runtime`, opening Harvest SQLite and querying its singleton even when inactive. C also has unconditional Harvest assignment rehydration in `main._home_hardware` and Harvest retirement on physical reset. These are **pre-existing B behavior**, not a P2C6A regression. The ordinary-mode boundary must remove this dependency before claiming no Harvest DB access/schema dependency.
- `Sending.confirm_piece_drop` returns early when a piece lacks allocation/project IDs, so it does not by itself open Harvest DB for an ordinary piece. Keep this distinction; not every Harvest import is I/O.

No tests were rerun: this analysis did not initialize any schema. P2C6A's recorded baseline run was 9 passed / 4 failed against the pre-slice module; the accepted run recorded the same failures. Inspection confirms the relevant planning/progress branches are already present in B and unchanged by P2C6A.

### Recommended comparison criteria

- Median of the three candidate/golden same-lot **useful PPM ratios >= 0.90**, with no individual pair below **0.85**. Report total PPM alongside it. Ten percent tolerates normal mechanical variation while rejecting a substantial loss from the reported continuous behavior; a 15% single-run floor catches severe tails. If golden itself is unstable or lot/order effects dominate, repeat the pair rather than declaring a pass from pooled totals.
- Unplanned pauses per 100 pieces must be no more than golden + **0.5**, and no more than **two additional pauses across the minimum 600-piece paired cohort**. Recovery/intervention pieces must be no more than golden + **one across that cohort**. Report counts and rates because these are small samples.
- **Zero** new persistent physical failure modes, lost custody, duplicate delivery credit or unsafe motion. No candidate-only repeated same-cause stall; one such persistent incident blocks the pass regardless of average PPM.
- No material useful-yield/misroute regression: no new confirmed wrong-bin event; unknown/reject rate no more than golden + **2 percentage points** without an explained lot/recognition cause and additional comparison. Do not promote unknown grouping into an exact piece count.
- Stage p95 > golden by **20%** or candidate DB budget miss triggers causal review even when aggregate PPM passes. It is not automatically a failure if independent mechanical overlap demonstrably hides the cost; document the evidence. Growing latency/RSS/queue depth or a timeout-dependent “successful” run is not accepted.
