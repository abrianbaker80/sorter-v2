## Scope and behavior

The slice-only `P2B.patch` builds on accepted P1 r2, P2A1 r2, and P2A2 r3. It adds `smart_bins_service.py`, `smart_bins_eligibility.py`, and `tests/test_smart_bins_reservations.py`; it changes only `smart_bins_migration.py` and `subsystems/distribution/positioning.py` among existing production paths. The legacy allocator calls the same pure content and dimension eligibility helpers as preview/reserve, but does not call the reservation service.

`preview(request, qualification)` and `reserve(request, qualification, expected_state_revision, expected_qualification_hash, request_key)` share candidate evaluation. A request carries the exact piece UUID, route attempt, **sorting-session ID** (the ledger FK, distinct from runtime `gc.run_id`), group key, positive integer quantity, pool, dimensions/global oversize flag, known custody references, and optional cancelled-predecessor reservation ID. A qualification carries machine/policy/artifact and routing revisions, current machine revision, a digest of existing local-state routing keys, an external reachability/settings revision, sharing option, and per-slot reachability, pool, limits, fit, cycle, and evidence. The caller must refresh this snapshot while holding the physical owner's outer locks. The service compares its digest with current local-state values and checks configured geometry, layer/section enablement, pool and limits on the same transaction connection. External reachability and the sharing option remain caller-qualified inputs; there is no separately writable configuration copy.

Reservations use `BEGIN IMMEDIATE`, foreign keys, and `synchronous=FULL`. One transaction rechecks session, policy, group, slot, attached open cycle, imported-cycle exclusion, projection blockers, recorded contents, held claims, and capacity. It prefers an eligible assigned match, then an occupied unlabeled match, then a genuinely empty bin, then permitted sharing. Known recorded contents are preserved on assignment. `misc` and globally oversize pieces get explicit virtual REJECT reservations with no physical assignment. Unknown or contradictory contents and unresolved receiving deliveries refuse admission. Count usage combines native **actual-cycle** deliveries, historical contributions, opening balances, and the four held states. A null count limit is unlimited.

The versioned, explicitly initialized service extension contains durable request/result receipts, cancelled-attempt links, and a trigger freezing reservation identity, destination, quantity, group/policy/routing references, and known custody fields. Exact request replay returns its stored result before stale checks; changed payload returns `IDEMPOTENCY_CONFLICT`. Completed or historically/native credited pieces cannot reserve again. Cancelled retries require a new route attempt linked to the latest cancelled reservation. `lookup_reservation` reads the durable record. `cancel_reserved` permits only `RESERVED → CANCELLED` with expected row revision, matching affirmative current-owner/non-dispatch evidence, and no release attempt row; it records audit, increments the machine revision, and leaves contents untouched. Rejections roll back without a partial assignment, claim, audit, or receipt.

## Validation

- `uv run --frozen python -m pytest tests/test_smart_bins_reservations.py -q` — **25 passed** (final targeted run). The initial 20-case run had 8 failures because refusal paths exited the caller-commit transaction without an explicit rollback; that was corrected before the passing runs.
- `uv run --frozen python -m pytest tests/test_smart_bins_reservations.py tests/test_smart_bins_storage.py tests/test_smart_bins_migration.py -q` — **90 passed** (final affected group).
- `uv run --frozen python -m pytest tests/test_bin_eligibility.py -q` — **26 passed** after factoring the shared helper.

Tests set temporary SQLite/configuration paths before imports, close connections and local-state keepers, and use real transactions. A barrier starts two independent connections contending for one unit: exactly one reserves; the stale loser retries with the current revision and still gets no capacity. Tests also cover reconnect replay, changed keys, historical/native/balance counting, held and terminal states, sharing/pool/fit, configuration and cycle gates, imported and unresolved evidence, cancellation, immutable facts, old extension rejection, and an injected receipt failure rolling back the entire claim. No full backend or frontend suite ran.

## Limits and P2C handoff

This service has no runtime callers and does not initialize at startup. Existing manual/profile/layout/history/Harvest assignment writers are **not yet fenced** and can bypass the ledger. The external reachability/settings revision and affirmative owner evidence are trusted inputs: P2C must produce them under the documented outer lock order, advance/revalidate revisions on every relevant change, bind active policy/group identity, and adopt committed routes only after the database transaction. P2C must also implement release intent, dispatch permits, exit evidence, completion, recovery, and reconciliation. An imported cycle, even with a numerical total, stays detached/unqualified here; no legacy data is migrated or repaired by P2B. The accepted later-native/opening-balance overlap limitation still requires reconciliation before operational adoption. There is no physical crash-safety or runtime-readiness claim.

Patch base and exact source/test hashes are recorded in `manifest.json`; `P2B.patch` reconstructs the result tree named there. This package publishes review artifacts only.
